The <DocsLink pkg="loaders" name="CommandLoader" decorated={false} /> scans a directory for command classes and returns a <DocsLink pkg="core" name="TopLevelCommand" decorated={false} />[] ready for `commandManager.addCommands()`.

## Folder structure

The loader expects a specific layout, following these rules:

1. Root-level commands are loaded as-is. They must be <DocsLink pkg="framework" name="AbstractStandaloneCommand" decorated={false} />, <DocsLink pkg="framework" name="AbstractParentCommand" decorated={false} />, or <DocsLink pkg="framework" name="AbstractContextMenuCommand" decorated={false} />.
2. A <DocsLink pkg="framework" name="AbstractParentCommand" decorated={false} /> may have a children folder with the same name as its `data.name`. The children folder must contain
<DocsLink pkg="framework" name="AbstractSubCommand" decorated={false} /> and/or <DocsLink pkg="framework" name="AbstractSubCommandGroup" decorated={false} /> classes, which are wired to the parent.
3. A <DocsLink pkg="framework" name="AbstractSubCommandGroup" decorated={false} /> may have a nested children folder with the same name as its `data.name`. The nested children folder
must contain <DocsLink pkg="framework" name="AbstractSubCommand" decorated={false} /> classes, which are wired to the group.
4. Any subdirectory that does not match a parent/group `data.name` is treated as an organizational folder and recursed into
as a new root, continuing the scan with the same rules above. This allows you to organize commands into subfolders without affecting
the command hierarchy.
5. Files with multiple classes have each class processed independently.

<Callout type="tip" title="About filenames">
The filenames are completely irrelevant for the loader. The command hierarchy is determined entirely by the `data.name` of each class and the folder structure.
</Callout>

Assuming the exported command classes have their `data.name` set the same as their file names, the loader will produce the following command hierarchy:

| File | Type | Notes |
|------|------|-------|
| `ping.js` | <DocsLink pkg="framework" name="AbstractStandaloneCommand" decorated={false} /> | Root-level, loaded as-is |
| `report-user.js` | <DocsLink pkg="framework" name="AbstractContextMenuCommand" decorated={false} /> | Root-level, loaded as-is |
| `mod.js` | <DocsLink pkg="framework" name="AbstractParentCommand" decorated={false} /> | `data.name === "mod"`, children folder matches name |
| `mod/ban.js` | <DocsLink pkg="framework" name="AbstractSubCommand" decorated={false} /> | Inside children folder, wired to parent |
| `mod/settings.js` | <DocsLink pkg="framework" name="AbstractSubCommandGroup" decorated={false} /> | `data.name === "settings"`, nested folder matches name |
| `mod/settings/view.js` | <DocsLink pkg="framework" name="AbstractSubCommand" decorated={false} /> | Inside children folder, wired to group |
| `utils/utils.js` | <DocsLink pkg="framework" name="AbstractStandaloneCommand" decorated={false} /> | Inside organizational folder, loaded as root-level |
| `utils/format.js` | <DocsLink pkg="framework" name="AbstractStandaloneCommand" decorated={false} /> | Inside organizational folder, loaded as root-level |

## Usage

By default, commands are automatically registered via `commandManager.addCommands()`:

```ts twoslash
import type { NyxBot } from '@nyx-discord/framework';
declare const bot: NyxBot;
// ---cut---
import { CommandLoader } from '@nyx-discord/loaders';

await CommandLoader.load({ bot, path: './dist/commands' });
```

Pass `register: false` to handle registration yourself:

```ts twoslash
import type { NyxBot } from '@nyx-discord/framework';
declare const bot: NyxBot;
// ---cut---
import { CommandLoader } from '@nyx-discord/loaders';

const commands = await CommandLoader.load({
  bot,
  path: './dist/commands',
  register: false,
});

bot.getCommandManager().addCommands(...commands);
```

## Writing commands for the loader

<Tabs items={['Top-level', 'Child']}>
<Tab value="Top-level">

Top-level commands (standalone, parent, context menu) are instantiated with no constructor arguments:

```ts twoslash
import { AbstractStandaloneCommand } from '@nyx-discord/framework';
import type { Metadata } from '@nyx-discord/framework';
import { SlashCommandBuilder, type ChatInputCommandInteraction } from 'discord.js';

export class PingCommand extends AbstractStandaloneCommand {
  data = new SlashCommandBuilder()
    .setName('ping')
    .setDescription('Replies with pong')
    .toJSON();

  async execute(interaction: ChatInputCommandInteraction, meta: Metadata) {
    await interaction.reply('Pong!');
  }
}
```

Alternatively, you can specify a `static create(bot)` factory:

```ts twoslash
import { AbstractStandaloneCommand } from '@nyx-discord/framework';
import type { Metadata, NyxBot } from '@nyx-discord/framework';
import { SlashCommandBuilder } from 'discord.js';

export class PingCommand extends AbstractStandaloneCommand {
  protected readonly data = new SlashCommandBuilder()
    .setName('ping')
    .setDescription('Replies with pong')
    .toJSON();

  public static create(bot: NyxBot) {
    return new PingCommand();
  }

  // ...
  // ---cut-start---
  public async execute(interaction: any, meta: Metadata) {}
  // ---cut-end---
}
```

</Tab>
<Tab value="Child">

Child commands (subcommands and subcommand groups) must accept a `parent` argument in their constructor:

```ts twoslash
import { AbstractSubCommand } from '@nyx-discord/framework';
import type { AbstractParentCommand, AbstractSubCommandGroup, Metadata } from '@nyx-discord/framework';
import { SlashCommandSubcommandBuilder, type ChatInputCommandInteraction } from 'discord.js';

export class BanCommand extends AbstractSubCommand {
  data = new SlashCommandSubcommandBuilder()
    .setName('ban')
    .setDescription('Ban a user')
    .toJSON();

  constructor(parent: AbstractParentCommand | AbstractSubCommandGroup) {
    super(parent);
  }

  async execute(interaction: ChatInputCommandInteraction, meta: Metadata) {
    // ...
  }
}
```

Alternatively, you can specify a `static create(bot, parent)` factory:

```ts twoslash
import { AbstractSubCommand } from '@nyx-discord/framework';
import type { AbstractParentCommand, AbstractSubCommandGroup, NyxBot } from '@nyx-discord/framework';
import { SlashCommandSubcommandBuilder } from 'discord.js';

export class BanCommand extends AbstractSubCommand {
  protected readonly data = new SlashCommandSubcommandBuilder()
    .setName('ban')
    .setDescription('Ban a user')
    .toJSON();

  public static create(bot: NyxBot, parent: AbstractParentCommand | AbstractSubCommandGroup) {
    return new BanCommand(parent);
  }

  // ...
  // ---cut-start---
  public async execute() {}
  // ---cut-end---
}
```

</Tab>
</Tabs>

The loader will call `static create` instead of the constructor if it exists. This allows you to access the bot instance,
or add logic, for example to inject services or other dependencies with a DI container.
