Many parts of the framework introduce the concept of a `MetaCollection`, which can store metadata about a given object, or about a given execution.

## ✅ Type Safety

Since a meta collection is just a `Collection<string | symbol, unknown>`, it's inherently unsafe by itself. For that reason, nyx uses the [`typed-field`](https://www.npmjs.com/package/typed-field) package, which creates a unique key, and only lets you set/get with a given type.

:::tip
The `typed-field` package is re-exported in `TypedFields.create()` method, so you don't need to install it separately.
:::

```ts
import { TypedFields } from '@nyx-discord/core';

// Fields with the same description won't collide
const myNumberField = TypedFields.create<number>('someDescription');

field.set(meta, 42);
// error-next-line
field.set(meta, 'foo'); // Argument of type 'foo' is not assignable to parameter of type 'number'.

const stored = field.get(meta);
//    ^? - const stored: number | undefined

// Throws if no value was set
const forced = field.get(meta, true);
//    ^? - const forced: number
```

## 🏠 Object Metadata

Most nyx objects implement a `getMeta(): ReadonlyMetaCollection` method. When creating your class, you can fill this with your own metadata, which can then be read by plugins or other entities to extract extra information about your object.

```ts
import { AbstractStandaloneCommand } from '@nyx-discord/framework';

class MyCommand extends AbstractStandaloneCommand {
  protected readonly override meta = new Collection<Identifier, unknown>([
    'someKey', 'someValue'
  ]);
  
  // ... other command logic
}

// Then, somewhere else, like in a plugin...

const meta = myCommand.getMeta();
const value = meta.get('someKey');
```

As a plugin developer, you may also choose to use the `TypedFields` API to create and expose a field:

```ts
import { TypedFields } from '@nyx-discord/core';

type MyPluginData = {
  someKey: string;
}

export const MyPluginDataField = TypedFields.create<MyPluginData>('myPluginData');
```

Then, a consumer of your plugin can use it to decorate their objects' metadata:

```ts
import { AbstractStandaloneCommand } from '@nyx-discord/framework';
import { MyPluginDataField } from 'my-nyx-plugin';

class MyCommand extends AbstractStandaloneCommand {
  constructor() {
    super();

    MyPluginDataField.set(this.meta, { someKey: 'someValue' });
  }

  // ... other command logic
}
```

Which then you'll be able to read with `MyCommand#getMeta()` and your field, safely.

## ⚡ Execution Metadata

Every "executable" object includes in its arguments an instance of a `MetaCollection`, which is passed around to middlewares and filters, so they can share data between them, and to your executed object.

Additionally, the `TypedFields` class contains constant fields that the framework uses to store framework-specific data. 

```ts
import { TypedFields } from '@nyx-discord/core';

// The bot who triggered the object (command, event, etc).
const bot: NyxBot = TypedFields.Bot.get(meta, true);

// The identifier of this object execution, which is a Symbol containing some debugable information.
const id: Identifier = TypedFields.Id.get(meta, true);

// The creation date of this meta, can be used as the execution start time.
const creationDate: Date = TypedFields.CreationDate.get(meta, true);

// Only for event middlewares and subscribers, whether the event was marked as handled by a subscriber.
const handled: boolean = TypedFields.EventHandled.get(meta, true);

// Only for event middlewares and subscribers, the EventBus that dispatched the event.
const eventBus: AnyEventBus = TypedFields.EventBus.get(meta, true);
```

Forcing these reads is safe for metadatas created inside the framework, but not for user-created metadatas, including those created by external [`EventBuses`](/features/events/event-bus) (since they're bot-independent).
