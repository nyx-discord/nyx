## Structure

The framework is split into four packages:

| Package                       | Purpose                                                                                                                            |
|-------------------------------|------------------------------------------------------------------------------------------------------------------------------------|
| `@nyx-discord/types`          | Defines all the object templates (interfaces) and their relations, acting as the blueprint. It has no implementations by itself.    |
| `@nyx-discord/base`           | Provides default, minimal implementations for the `types` interfaces, making them directly usable.                                 |
| `@nyx-discord/djs`            | The [discord.js](https://discord.js.org) adapter, connecting the framework to a discord.js `Client`.                                |
| `@nyx-discord/djs-core`       | The [@discordjs/core](https://discord.js.org/docs/packages/core/main) adapter, connecting the framework to a raw `Client`.          |

This separation is done to allow for easy replacement of implementations, so you can use your entirely custom components without depending on the default (`base`) one at all. The adapters only exist to plug the framework into a specific Discord library.

## Which package to use?

Most of the time, you'll want to use an adapter, depending on the library your bot uses:

<Tabs items={['discord.js', '@discordjs/core']}>
  <Tab>
    If your bot uses [discord.js](https://discord.js.org), install `@nyx-discord/djs`:

```npm
    npm i @nyx-discord/djs discord.js
```
  </Tab>
  <Tab>
    If your bot uses [@discordjs/core](https://discord.js.org/docs/packages/core/main), install `@nyx-discord/djs-core`:

```npm
    npm i @nyx-discord/djs-core @discordjs/core @discordjs/rest @discordjs/ws
```
  </Tab>
</Tabs>

Both adapters re-export `types` and `base`, so you can import everything from a single package.

<Callout>
  Throughout this guide, code examples use `@nyx-discord/djs` by default. If you use `@discordjs/core`, simply swap the import to `@nyx-discord/djs-core`: the library-agnostic APIs (filters, middlewares, schedules, plugins, events) are identical, and only the parts that touch Discord's client or interactions differ.
</Callout>

If you want to develop something for nyx, such as a plugin, you can use `@nyx-discord/types`. This way, you can depend on the interfaces and not any actual implementation, ensuring your component will work across all adapters.

## Object nomenclature

There's also a difference of nomenclature between the packages:

- `@nyx-discord/base` has objects prefixed by `Abstract`, `Default` or `Basic` (for example, <DocsLink pkg='base' name='AbstractSubCommand' decorated={false} label={<code>AbstractSubCommand</code>} /> and <DocsLink pkg='base' name='DefaultCommandManager' decorated={false} label={<code>DefaultCommandManager</code>} />). This means that they're base implementations of their respective interfaces. Specifically:
  - `Abstract` is self explanatory. It needs to be extended to be used, often used by user-defined objects like commands or subscribers.
  - `Basic` is a basic implementation of an interface, and can be directly extended, with nothing else needed to customize it.
  - `Default` is a basic implementation but it's used somewhere internally, so to extend it [you'll also need to inject it](/extend).
- `@nyx-discord/types` has almost no implementations, and no prefixes either (for example, <DocsLink pkg='types' name='SubCommand' decorated={false} label={<code>SubCommand</code>} /> and <DocsLink pkg='types' name='CommandManager' decorated={false} label={<code>CommandManager</code>} />). These are the base interfaces for any implementation.

When you want to specify a type, prefer using `@nyx-discord/types`, eg. `consume(cmd: SubCommand)` instead of `consume(cmd: AbstractSubCommand)`, since it'll work across implementations and adapters, and aligns with [Dependency inversion](https://en.wikipedia.org/wiki/Dependency_inversion_principle): objects shouldn't depend on implementations, only on base interfaces.
